# 代码与性能优化计划

## 范围与状态

本计划覆盖数据库锁修复，以及大表查询与展示、异步导出、连接池、运行健康检查、通知可靠性、认证与权限六项优化。
不包含新增客户预算、月结账单、预测或利润分析；这些属于另行确认的产品功能。

- 锁修复：已完成本地代码与隔离 PostgreSQL 回归测试，本次单独提交；尚未部署。
- 其余阶段：待实施，不代表已经提供对应接口、表或后台服务。
- 后续表名与接口为设计建议，实施时按兼容性评审确认；新增迁移从下一个未使用编号开始。

## 不变的边界

- New API 原库保持只读；用户配额仍经官方接口修改，不直接写用户表。
- 独立监控库增量升级，不清空归档、规则、配置或执行记录。
- 保持实际消费金额、请求历史价格、缓存数学配平、分组归属和 Excel 精度的既有口径。
- 余额 API 每次实时计算，不加余额缓存；当月实时查、历史用归档，仍保持每天北京时间 10:00 或手动触发告警检查。
- 定时配额仍按原周期执行，不因服务启动补发，不重试不明确的额度请求；五人并发分组方式不变。
- 页面路径、域名和端口跳转方式不变；已部署的 Nginx 入口保持兼容。
- 继续使用宽范围 requirements.txt，不以本计划引入依赖锁文件。
- 部署目标单独确认；部署后只做 CLI/API 验证，不自动开浏览器。

## 阶段 0：锁冲突修复（本地已完成）

将 advisory lock 常量集中到 `locks.py`，保持余额锁与通知锁编号不变，定时配额领导锁改用独立编号。
新增测试覆盖编号互斥、通知实际使用独立锁、两个调度器互斥、调度器与余额事务锁互不阻塞，
以及持有调度器锁时两种渠道的测试通知和报警通知均可完成。
外部发送与真实额度修改一律 mock，数据库测试只使用隔离 fixture。

上线无需新 SQL。必须先停止并确认所有旧 quota-worker 退出，再升级服务并启动新 worker，
避免旧、新领导锁不同造成两个调度器并行。具体说明见[升级与备份](upgrading.md)。

## 阶段 1：运行状态与性能基线

**工作**

- 保留 `/healthz` 为轻量存活探针，增加就绪检查；未配置的可选功能不使基础统计服务被误判为不可用。
- 增加仅管理员可见的运行状态：原库/监控库连通性、迁移版本、调度器活动状态、最近执行与通知结果。
- 必要时在监控库增加 `worker_status`，记录角色、实例、领导/待命、心跳和最近执行状态；不记录凭据。
- 建立可重复的虚构大数据测试集，记录查询时长、P50/P95、响应体积、浏览器渲染开销及峰值内存。
- 对余额/通知/定时配额同时工作及异常场景做跨模块集成测试。

**验收**

数据库断开、迁移缺失、worker 不活动均有明确状态，不再只显示无条件的 ok。
状态检查只检查连接或元数据，不产生消费统计、余额告警或配额修改。
真实浏览器性能测量如有需要单独安排，不在部署后自动打开浏览器。

## 阶段 2：数据库连接池与统一访问层

**工作**

- 建立 `db.py`，分别管理 New API 只读库和监控库的小型连接池。
- 连接池在 Gunicorn 子进程启动后初始化，明确每个进程与后台 worker 的连接预算。
- 统一连接/排队/语句超时、事务清理、断线重连和优雅关闭；配置可回退到直连模式。
- 会话领导锁与 LISTEN/NOTIFY 保留独立长期连接，不随普通池借还或事务级代理切换。

**验收**

并发请求不无限创建连接，异常后连接和事务正确回收，无串事务或只读设置丢失。
用同一基线对比建连次数、连接等待和接口 P95；不以猜测的倍数承诺收益。

## 阶段 3：大表查询、分页与展示

**工作**

- 先检查已有索引与查询计划，再决定 SQL 优化；不会自动修改 New API 索引或结构。
- 原库索引变更如确有必要，另行评审空间、锁影响、窗口和回退方案。
- 对模型/用户多选等明细筛选尽可能前推，保留页面顶部统计与表格局部筛选的范围区别。
- 汇总、排名、明细分页分开返回，稳定排序与分页标识包含模型、令牌及历史价格分行信息。
- 对大表引入虚拟滚动，减少 DOM 节点；全选和按组选择仍作用于完整筛选范围，不仅是当前页。
- 评估悬浮详情按需加载；详情必须对应当前报表快照，不能重查出另一份 Token、倍率或价格。

**验收**

不能先限制日志条数再聚合，不能把当前页当全量合计。
分页前后及不同聚合模式的金额、Token、请求数、筛选结果一致。
历史价格拆行、令牌汇总、多选禁用用户的规则、金额显示与详细精度均不退化。

## 阶段 4：异步报表导出

**工作**

- 增加独立监控表 `export_jobs` 与可选 `report-worker`，请求返回任务 ID，页面展示进度并下载结果。
- 冻结筛选条件、账本范围、统计截止点、价格/倍率配置版本，明确查询快照和生成时间。
- 保留同步导出兼容入口；大报表转后台队列，后台并发及资源独立限额。
- 文件保存在专用持久目录，不把应用源码目录改为可写；配置有效期与清理策略。
- 下载按任务所有者与管理权限校验，不开放裸文件目录，不保存 Basic 密码或 PAT。
- 使用分块查询和受控临时文件降低内存；流式工作簿模式需核对现有合并单元格等限制，
  不能为采用某种导出库而擅自破坏现有样式。

**验收**

大报表不占用普通 Web 请求直到超时；任务失败可查，过期文件不可下载。
多工作表、列顺序、显示名、SUM 合计及原精度保持；导出过程不修改账务数据。

## 阶段 5：通知队列与发送记录

**工作**

- 在监控库新增 `notification_jobs`、`notification_attempts`；当前报警仍保留最新一条，发送历史独立保存。
- 报警事务提交后创建通知任务；独立发送进程取任务，发送网络请求时不长期持有配置行事务锁。
- 保存脱敏状态、结果与时间，不保存 Secret、完整 Webhook URL、PAT 或原始远端响应。
- 派发前检查报警版本及是否已恢复，避免积压消息发送过期告警。
- 根据渠道实际幂等能力采用固定消息标识或保守处理；不能保证所有渠道只发送一次。
- 对明确可安全重试的失败退避重试；结果不明确时不盲目重发，提示人工核对。

**验收**

通知失败不回滚报警或归档，慢网络不阻塞设置保存，任务不丢失且有失败说明。
报警检查触发方式与频率不变，禁用渠道或恢复额度后不会继续发送旧报警。

## 阶段 6：认证、安全与权限

**工作**

- 登录失败按账号与可信来源地址限速；只信任已配置代理，防止伪造转发头绕过。
- 统一所有写操作的 JSON、来源及防 CSRF 校验；敏感基础校验随前面阶段尽早完成。
- 保留 Basic Auth 与既有 PAT Bearer API 兼容；评估可选的短期网页登录会话，提供明确退出与撤销。
- 可选会话只保存随机令牌的安全摘要和必要状态，不存管理员明文密码或 PAT；
  每次访问仍检查 New API 账号状态、角色与密码变更，不能绕过上游账号安全策略。
- 监控库保存本应用的权限映射，区分查看、手工额度修改、定时规则及全局设置；
  不写 New API 用户角色。首次升级保留已有权限，超级管理员可收紧授权。
- 导出下载、运行状态及新的后台管理接口一并做权限回归测试，不仅保护页面。

**验收**

未登录、停用、降权、修改密码、退出会话及跨站写入均受正确限制。
只读用户不能通过直接调用接口改额度；既有对外余额/报警 API 仍用 New API PAT。

## 实施与交付节奏

阶段 0 单独作为补丁，不等待后续大优化。之后按 1 → 2 → 3 → 4 → 5 → 6 推进，
认证安全基础校验提前穿插；每阶段独立实现、验证、文档与迁移评审，避免一次大改难以回退。

每阶段交付：本地回归结果、基线对比（涉及性能时）、新增表/配置清单、兼容入口与回退步骤。
新增服务默认明确启用，不擅自增加公开端口或改变现有功能的执行频率。
Git 提交、部署目标和正式发版按用户后续指令执行。
