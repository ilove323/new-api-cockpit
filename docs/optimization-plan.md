## 不变的规则

- 不更改计费日志、金额或余额统计口径，不自动重发有副作用或收费的请求。
- KEY 管理保留手动查询，以及每次修改前、后的实时查询；不加二次确认或插件冷却。
- 认证与权限不跨请求缓存；同一请求内允许复用已经验证的数据。
- 不把用户密钥、密码或私有站点清单写入源码、日志和公开文档。
- 存储优化不能复活已经删除的附件，不能把新事件交给不兼容的旧版本写入。

## KEY 配置的配套修复

经确认修复改组覆盖额度的问题，不再仅列为上游依赖。

- Cockpit 改组、配置编辑和 VSIX 改组只提交 `PATCH /api/token/:id` 的配置字段，不回写查询到的额度；正常消费不再被当作配置预览冲突。
- 增加基于官方 rc.47 固定提交 `e835b1bfc43b565d625537830dbfb19328925134` 的 [New API 补丁](../patches/new-api/README.md)。服务端锁定目标记录，仅更新配置列；Redis 原位更新配置，不清空实时预扣计数。中断、回滚与丢失回执按实际提交状态读取恢复，不重复写入。
- 路由仍限本人，要求原有身份校验及新式 PAT 的 `api_key:write` 权限，保留操作审计。没有增加管理员跨用户 KEY 接口。
- 跨用户 KEY 管理继续按现有方式取得 owner PAT。官方 rc.47 称 `users.access_token` 存储为 Legacy，并有 `LegacyAccessTokenRetireAt` 策略；这不是当前站点 PAT 已失效的结论。本轮未改变 PAT 获取、撤销或退役设置，也没有凭空设计替代接口。
- 新接口必须随配套 New API 更新；原服务端 404/405 时明确报错，绝不回退到完整 PUT。主动调整 KEY 限额，以及其他仍使用原 PUT 的客户端，不在此次配置 PATCH 的修复范围内。
- 源码补丁、原许可、固定版本及验证入口独立放在 `patches/new-api/`，未修改任何站点正在运行的 New API。

## 清理与复用结论

- `manual.py` 直接引用当前令牌集成模块；原个人令牌及图片入口保留为指向同一模块对象的兼容别名，无第二份业务实现。已有导入/替换依赖和边界回归，不能按“旧文件”直接删除。
- 报表、选项和异常日志回退已共用 `report.scoped_sql`。保留全部渠道、空范围和未知渠道的语义差异，不把质量查询等不同统计口径强行并入一个构造器。
- 源码归档补齐本地/私有配置、证书和密钥文件的排除规则，保留公开 `.env.example`；使用虚构目录实际构建 sdist 和 Git archive，避免读取真实站点清单。一次性测量脚本不提交；配套补丁的可重现验证脚本单独维护。

## 执行顺序

1. 正确性、认证和部署模板：小范围改动及对应回归。
2. 请求次数：记录冷/热缓存、并发和恢复请求预算，再合并重复路径。
3. 聊天性能：存储和页面分开验证，保留旧历史和中断恢复。
4. 清理、文档和安装包：同步 VSIX 与镜像内下载内容。发布与部署另行执行。

## 尚未收尾与发布边界

- 冷缓存或索引本身超出常驻上限的历史仍完整验证；当前改动不是持久磁盘索引，也不承诺任意规模首次打开都为常数开销。
- KEY 配置修复需要配套发布 New API 补丁镜像，不能只发布客户端；owner PAT 流程保持不变。限额主动增减仍非原子操作，未扩展为本次会计更新协议。
- 发布、推送及生产部署需要另行执行；本轮仅本地开发分支提交。
