# 渠道质量

从侧边栏进入 `/cockpit/quality/`，比较同一日志模型在不同上游、渠道的调用结果。
默认近 24 小时，按模型、渠道列出明细，当前启用渠道的上游在同一列表展示。
流式和非流式调用一起展示，范围独立于用量统计所选账本、计费分组和档位。
渠道 ID 是身份，名称、标签和启用状态取当前 New API。列表显示渠道名称和 ID，只列启用渠道（`status=1`）；
禁用、已删除和未知渠道不进入列表或渠道筛选选项，汇总使用同样范围。
默认查询只读取源库；接口指定 `channel_status=all` 时才读取监控库存，补充已删除渠道的最后名称和标签。
每次查询重新读取渠道状态，启用或禁用后重新查询即可更新。原始日志、账务归档和余额统计不受这里的范围限制影响。
质量分析不应用余额账本的渠道排除规则，不调整路由、额度、渠道状态或原账单。

## 使用

1. 修改时间后点击查询；也可以使用近 24 小时、近 7 天按钮。
2. “同模型渠道对比”标题下方提供模型和渠道两个多选筛选，勾选或取消勾选立即查询，不需要再点查询按钮。没有勾选表示全部。
   筛选沿用最近一次查询的时间，不自动提交尚未确认的时间输入。关键词搜索只筛选下拉选项，区分大小写、按原文包含匹配；后端选中值精确匹配。
3. 列表显示请求次数、成功率、失败码、日志费用，以及“首字/总耗时 P50”“首字/总耗时 P95”和平均 token/s。
   每列的两个值依次是该分位数的首字耗时和总耗时，例如 `100ms / 5s`；缺少某项时只将该项标为“无数据”。
   失败码及次数逐项列出，例如 `400 29次`。
4. 操作列只有“查看日志”，进入同站点 New API 日志，按该行模型、渠道和当前统计时间筛选。

时间使用北京时间，包含选择的结束秒，单次最多 31 天。没有自动刷新；列表每页 50 行。
发起新查询会取消旧请求，旧响应不能覆盖新结果。日志跳转使用已显示结果的时间，
不会偷偷改成尚未提交的输入值。
接口的 `warnings` 提供数据缺失说明；页面只显示查询错误，不用零值或旧结果代替失败查询。

## 性能健康

面板展示成功率、平均延迟、吞吐量，以及流量最高的六个模型及其成功率。
默认对应近 24 小时，修改时间或模型、渠道筛选后，面板与表格一起更新，不固定查询另一个 24 小时窗口。
请求次数、失败调用和日志费用另列汇总，表格操作只有“查看日志”。

- 成功率按成功次数 /（成功 + 失败）计算，取消或无法判断结果的调用不进入分母。
- 平均延迟用有效成功调用的总耗时合计 / 样本数，范围与总耗时 P50/P95 相同；
  不平均各渠道的均值或中位数。没有输出 Token 的调用仍可提供有效延迟样本。
- 吞吐量沿用平均 token/s 的口径，单位 `t/s`，包含首字等待；不把无输出 Token 的调用加入速度样本。
- 高频模型按当前范围的渠道调用次数排序，同模型先合并全部渠道再计算成功率，最多列六个。
  不按金额或当前表格分页排序；同一请求的重试仍属于多次渠道调用。
- 没有有效数据时显示“无数据”，没有调用时模型列表显示“暂无请求数据”。

外观参考 New API 的[性能健康面板](https://github.com/QuantumNous/new-api/blob/v1.0.0-rc.42/web/src/features/dashboard/components/overview/performance-health-panel.tsx)，
页面、样式和汇总独立实现，图标使用项目已有 ISC 许可的 Lucide 资源。
这里读取日志还原渠道调用，不读取官方按模型/计费分组采样的性能汇总，两个面板的统计范围不能直接混比。
健康面板复用同一次只读查询，不新增请求、采样任务或数据库表。

## 调用和成功率

New API 的消费记录 `type=2` 不必然表示正常完成，流式请求可能已经消费但断流。
错误记录为 `type=5`；如果关闭记录、日志已清理或错误未落库，Cockpit 无法补回。
这里是**日志口径**，不是网关完整的用户请求可用率或 SLA。

有 `other.admin_info.request_policy`（也兼容顶层 `request_policy`）时：

- 同一请求的多条日志取路由事件最完整的一份，按请求 ID、尝试序号和渠道归并。
- 一个尝试里的选择、失败、重试决策不重复计数，失败到另一个渠道成功保留两次渠道调用。
  先还原完整重试链，再按当前启用状态筛选渠道；排除前序禁用渠道不会把最终成功误当作无重试样本。
- 明确成功、失败（含 HTTP 400 等业务拒绝）、客户端取消、状态未知分别在后端计数。
- 客户端主动断开不放入成功率分母；明确的参数/上下文/内容策略拒绝与上游密钥、额度、限流和服务故障均算失败。
  违禁计费记录不冒充上游失败。错误元数据不充分时不承诺精确归因。
- 无法确定原因的 `incomplete` 响应归为未知，不直接当作失败或成功。

成功率 = 成功 /（成功 + 失败）。页面不展示排除/未知列；API 保留 `ignored_count` / `unknown_count` 以解释成功率分母，`outcome_coverage` 表示能识别结果的比例。
失败 / 错误码优先读取当前尝试的 `status_code`（兼容 `status`），缺失时关联同请求、同渠道、同尝试的错误日志，使用与用量统计相同的 `logs.other.status_code`，不会把最终渠道的错误码归给别的渠道。
按 `400 29次`、`500 3次` 等格式列出 HTTP 4xx/5xx；没有 HTTP 状态码但有业务错误码时显示原错误码。
HTTP 200 后的流式响应仍可能失败；原日志未记录错误码时显示“流式失败（未记录错误码）”，不能推测成 500。其它证据不足的失败保留“未知”。

页面“请求次数”按渠道调用尝试计数，同一用户请求发生重试时可能产生多次渠道调用。
API 的 `unique_requests` 在总汇总中对请求 ID 去重，不能把各渠道的去重数相加当作用户请求总数。

旧日志没有可用路由事件时采用消费/错误记录口径：明确非流式消费或正常流式状态算成功，
明确错误算失败；没有流式状态或元数据损坏的记录可能归为未知。
API 保留旧日志数量；这些记录无法恢复完整的渠道重试过程。

路由和流式状态识别参考 New API `v1.0.0-rc.42` 的[性能结果分类](https://github.com/QuantumNous/new-api/blob/v1.0.0-rc.42/pkg/perf_metrics/outcome.go)
和[路由事件](https://github.com/QuantumNous/new-api/blob/v1.0.0-rc.42/service/request_policy.go)。
实现独立编写，只使用已有日志字段，不复制官方组件或采样进程。
官方性能汇总按模型、计费分组统计最终请求结果，并排除部分业务拒绝；这里按渠道 ID、当前标签还原调用尝试，明确错误均计入失败，两个数字不能直接混比。

## 耗时

- **总耗时**：路由事件的结束 `elapsed_ms` 减去本次选择渠道的开始 `elapsed_ms`。
  这是一次渠道调用在网关内的耗时，包含转发处理，不是纯网络往返时间。
- **旧日志耗时**：`use_time` 是整数秒；只有正值作为有效样本。零可能是不足一秒或没有记录，不能冒充精确零耗时。
- **首字**：采用流式消费日志 `other.frt` 的首响应时间，单位毫秒，取正值。只采用确认没有重试的成功调用，
  不把含前序失败等待的首响应时间全归给最后一个渠道，也不承诺它一定是首个正文 Token。
- 页面总耗时只采用确认无重试的成功调用，避免前序失败等待影响渠道对比。接口可通过 `latency_scope=all` 纳入其它成功调用，但旧日志可能包含整个请求耗时。
- P50/P95 对各自有效原始样本计算。上游和总汇总重新计算，不平均渠道分位数。
- 无有效样本返回 `null` / “无数据”；样本较少时分位数代表性有限，API 保留样本数量供核对。

## 平均 token/s

平均速度 = 有效成功样本的输出 Token 合计 ÷ 同批样本的渠道调用耗时合计（秒）。
这项速度包含首字等待，是端到端输出速度，不是排除等待时间后的纯生成速度。流式、非流式采用同一口径；
只计 `logs.completion_tokens`，不把输入或缓存 Token 加进去，也不除以报表时间跨度。

- 页面只用确认无重试的成功调用。接口指定 `latency_scope=all` 时，可用路由事件的本次尝试耗时计算重试后的成功调用。
- 输出 Token 仅归到最终消费记录对应的最后一次渠道尝试，不分给前面失败的渠道。
- 输出 Token 或耗时缺失、非正，结果为失败、取消或未知，都不参加速度计算。旧日志不能拆开重试耗时的，也不参加。
- 上游、总汇总和小时趋势重新累加 Token 和耗时后求比值，不平均各请求或各行速度，避免短请求被过度放大。
- 页面只显示速度，无有效样本为“无数据”；API 保留样本量、覆盖率。

API 的小时趋势按选中日志的落库时间归入北京时间小时，只列有记录的小时。
不同输出长度、上下文、推理强度及请求方式都会改变耗时，不能直接把流量组成不同的渠道当成公平测速。

## 费用与价格

日志费用取文本消费记录 `quota / 500000`，不因取消、断流或质量分类而删除已记录费用。
这是站点扣费，不是上游采购成本。金额列表两位小数，API 数值保留原精度。

页面列表不加载历史价格组合。`trends` 接口按请求当时的价格快照、计费分组和倍率列出价格组合。沿用现有历史价格解析，
不使用当前价格填补旧日志；表达式不支持、价格无法还原或元数据损坏时单价留空，金额仍保留。
单个模型/上游组合最多列出记录数最多的 100 个价格组合，`price_bucket_count` 返回实际组合数，费用合计不截断。

渠道标签不是计费分组。日志模型名也不保证渠道映射后的实际模型相同；做价格/质量比较时应核对模型映射，
不同倍率、档位及用量组成仍会影响记录中的价格和速度；看板汇总这些调用，不按计费条件删掉其中一部分，不能仅按总费用判定谁更便宜。

## 数据库和查询边界

不新增表或迁移，不写 New API 数据。源库依然只需要 `logs`、`channels` 的 SELECT 权限；
`request_id`、`is_stream`、`use_time`、`completion_tokens` 不存在时对应能力降级，API 的 `warnings` 说明缺少字段。
监控库只读取渠道库存和标签，不引入定时采样或后台工作容器。

正常路径在同一个只读、可重复读快照中用 PostgreSQL 聚合，源日志只读取一次。
每条语句最多 30 秒；结果超过 1000 个模型/渠道组合时要求缩小范围，不提供部分合计。
异常 JSON 才进入有界回退：同一快照流式读取，最多 100,000 条或约 32 MiB，再用数据库重新聚合；
超过上限返回 503，不跳过异常费用。没有新增源库索引；应按实际查询计划决定，不能盲目建索引。

质量分析仅比较文本生成，已知图片、异步任务、嵌入和实时会话路径不混入质量分母。
没有路径的旧记录保留并按旧日志口径处理。
历史日志删除后，月度金额归档无法重建质量指标；目前不保存独立质量历史。

接口参数和调用方法见 [API 参考](api.md#渠道质量接口)，也可以在 `/cockpit/docs/` 的“渠道质量”分类试用。
