# 用户配额

`/quota/` 是独立的管理员页面；统计页右上角的“用户配额”按钮可切换进入。
Nginx 需要按 [部署文档](deployment.md) 把 `/quota` 和 `/quota/` 转发给统计容器。
已核对 New API 当前源码：没有占用顶层 `/quota` 路由；升级 New API 后应再次检查路由冲突。

页面读取 New API `users` 表中的未删除用户、显示名、用户组、状态、剩余额度与已用额度。
状态下拉框支持多选，默认只查看启用用户；只有勾选“禁用”后，禁用用户才会
出现在列表并可被全选或按组批量选择。取消某个状态时，该状态下已经勾选的用户
也会被移出操作名单；两个状态都取消则列表为空。用户组人数按当前状态范围计算。
可在“选择用户组”中勾选一个或多个组，再批量选中或取消组内用户；该操作
遵循状态筛选、不受搜索框影响，仅改变页面上的用户勾选，不会自动调整额度。没有批量选择人数上限。
统计容器的数据库账号仍然只需要 `SELECT` 权限。余额按 New API 的
`500000` 额度单位 = `1` 元展示；输入金额必须能精确换算为整数额度单位。

选择用户，输入每人增减金额，先预览，再确认执行。预览中的“变更后”
只是当前数据库余额加减金额的估算；实际执行由 New API 原子增减接口读取最新余额，
**不会把预览值覆盖到用户账户**。减少额度可能产生负余额。

应用在服务器端读取当前登录管理员已有的 New API PAT，通过内部地址
`NEW_API_INTERNAL_URL` 调用 `POST /api/user/manage`，请求体使用
`action=add_quota`、`mode=add|subtract` 和整数 `value`。PAT 不返回浏览器，
也不写进统计项目配置文件。如果当前管理员没有 PAT，页面会明确报错，需要先在
New API 生成 PAT；不会改用 SQL 修改额度。New API 自身检查操作者对目标用户的权限，
统计服务也会在调用前拦截明显无权操作。

确认一次后，页面按用户 ID 将名单分成每组最多 5 人，每组发给统计服务；服务端
并发调用这组用户各自的 New API 接口。等整组全部返回后才开始下一组，因此
人数多也不会被塞进一次长 HTTP 请求。页面显示进度及每个人的执行结果。
任何请求失败或结果不明确时，仍收集当前组其他已发出的请求结果，但不再发后续组，
不自动重试。这不是跨用户事务；已经成功的额度不会自动回滚。执行期间不要刷新、
关闭页面或重复操作；若页面中断，已经发出的请求可能仍在执行，尚未发出的组不会自动续跑。
此时必须先核对实际余额和
New API 审计日志，再决定是否重新操作。浏览器确认页和请求头防护用于防止误点及
跨站表单提交，但不代替管理员对操作对象和金额的复核。

## 定时额度修改

右上角齿轮包含“定时额度修改”和“执行记录”两个标签页。
用户组来自 New API `options.GroupRatio` 和未删除用户的 `users.group`，不是渠道标签。
新增规则选择一个或多个组、周期、增加/减少、每位用户金额及是否启用。

| 周期 | 北京时间执行时间 |
|---|---|
| 每天 | 每天 00:00 |
| 每周 | 每周一 00:00 |
| 每月 | 每月1日 00:00，按自然月计算 |

- 新建或重新启用规则只安排严格晚于保存时间的下一个周期，不立即调整额度。
- 编辑已启用规则且周期未变，保留既有下次执行时间；只影响尚未生成的任务。
- 执行时冻结规则，再实时读取组内启用、未删除用户，去重生成逐用户记录；每组请求前复核状态、用户组和管理员权限。
- 这是每位用户的金额，不是整组共享的总金额；不同规则命中同一用户时分别执行，金额累计增减。
- 普通管理员只可修改自己执行的规则；超级管理员可管理全部规则。保存或重新启用后，执行管理员绑定到当前操作账号。
- 不在规则或 `.env` 保存 PAT；按管理员 ID 从 New API 数据库读取最新 PAT，每个请求组开始前重新读取。管理员改名不会丢失绑定。
- 管理员停用、删除、权限不足、无 PAT、所选组消失，任务报错，不绕过 New API 接口直接写余额。
- 无符合条件的启用用户时，记录零用户成功，不产生额度变更。
- 停用或删除可阻止尚未开始的任务；已经执行的增减不会撤销。规则软删除，历史快照和逐人记录保留。

### 执行记录与失败处理

每组最多 5 人并发；当前组全部返回并保存结果后才处理下一组。结果包括成功、失败、结果不明确、未发起。
每个请求发出前，先提交数据库中的“请求中”状态。进程中断后不续跑：
已经保存的成功结果保留，仍为请求中的用户标记“结果不明确”，未发起的用户标记“未发起”。
执行记录支持分页查看全部历史及逐用户结果，金额表格按两位小数展示。

New API 增减接口不提供本功能所需的请求幂等键。因此不能承诺数据库与远端额度严格跨系统“只生效一次”；
网络断开或响应异常可能发生在额度已变更之后。**不自动重试、不自动回滚，也不提供一键重跑不明确请求**，必须先核对 New API 审计日志。

定时任务允许最多 5 分钟的启动延迟（通常用于进程启动/调度延迟），超过窗口的周期记录为未执行，跳到下一周期，
不累计补发停机期间的额度。配置变更通过 PostgreSQL `LISTEN/NOTIFY` 唤醒调度器；最长 30 秒的等待上限仅用于
响应停止信号及重新核对任务元数据，不进行余额报警、消费统计或用户额度的周期性轮询。

### 部署与数据库

使用现有独立监控数据库 `MONITOR_DATABASE_URL`，新增 `007_quota_schedules.sql`：
`quota_schedule_rules`、`quota_schedule_rule_groups`、`quota_schedule_runs`、`quota_schedule_run_items`。
沿用 `schema_migrations` 增量执行，旧月度归档、余额设置和用户数据不清空。

| 表 | 存储内容 |
|---|---|
| `quota_schedule_rules` | 是否启用、周期、增减方向、整数额度单位、执行管理员 ID、下次执行时间、版本及软删除时间 |
| `quota_schedule_rule_groups` | 每条规则选中的用户组名称；规则与组名联合唯一 |
| `quota_schedule_runs` | 每次计划执行的规则快照、状态、结果计数与时间；规则 ID 和计划时间联合唯一 |
| `quota_schedule_run_items` | 执行时的用户与组快照、整数额度单位、逐用户请求状态及时间；执行 ID 和用户 ID 联合唯一 |

原有余额、渠道及月度归档表无需改列。规则金额以整数额度单位保存，表格两位小数只是展示格式。
四张表均不存管理员密码或 PAT；执行记录仅保留脱敏结果，不保存远端原始响应。

```bash
# 一个容器包含网页与两个内置定时器；启动入口自动应用增量迁移。
docker compose up -d --build statistics
docker compose logs --tail 100 statistics
```

配置监控库后，配额定时器随应用启动，不需要额外容器或 profile。
设置页提示“定时器随服务自动启动，无需单独部署”。保存规则只安排下一周期，
不是手动启动定时器；关闭浏览器不会影响已启用规则的后台执行。
Gunicorn 在子进程初始化后启动后台线程，不在模块导入或 HTTP 请求中启动，也不在 fork 前建立数据库连接。
各网页进程均可待命；PostgreSQL 会话锁保证只有一个配额调度器实际执行。余额定时器使用不同领导锁，
仍每天北京时间 10:00 检查。SQL 迁移、余额事务、通知发送和两种调度领导锁互不复用。

进程收到退出信号后停止领取任务与发起下一组请求，保留当前组保存结果的时间；
应用升级会暂时停止定时任务，既有不补发、不续跑、不重试不明确请求的边界不变。
`/healthz` 会检查当前网页进程的两个调度线程，以及数据库里两种调度器是否都有领导者；
配置监控库但调度未就绪时返回 `503`，不再仅凭网页可访问认定功能完整运行。
没有监控库时不启动定时器，手工额度和基础统计仍可用。
完整探活示例见[运行状态检查](deployment.md#运行状态检查)；探活不会执行额度修改。

非 Docker 部署使用统一入口，自动加载 Gunicorn 生命周期配置：

```bash
python -m new_api_statistics.runtime gunicorn --bind 127.0.0.1:8000 new_api_statistics.app:app
```

如自行指定 `--config`，需在自定义配置中引入 `new_api_statistics.gunicorn_conf` 的
`post_worker_init`、`worker_exit` 和 `graceful_timeout`，不得遗漏启动/退出钩子。
`python -m new_api_statistics.app` 的直接启动也会管理定时器，但不建议将 Flask 开发服务器用于生产。

使用发布镜像时，Compose 与镜像必须来自同一版本。当前单容器改动尚未发布，
不能用新模板启动不包含定时器生命周期的旧 `0.1.3` 镜像。
旧部署切换前停止旧 `balance-worker`、`quota-worker` 并确认退出，见[升级说明](upgrading.md)。
所有页面、静态资源和管理 API 的认证及请求来源检查保持原样，无新增端口或 Nginx location。

### 管理接口

以下接口用于管理员设置页面，不是模型调用接口；使用相同的管理员 Basic Auth。
写请求须包含 `Content-Type: application/json` 和 `X-Quota-Action: schedule`。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET / POST | `/quota/api/schedules` | 读取规则及用户组选项 / 新建规则 |
| PUT | `/quota/api/schedules/<id>` | 编辑规则 |
| PATCH | `/quota/api/schedules/<id>` | 启用或停用规则 |
| DELETE | `/quota/api/schedules/<id>` | 软删除规则，保留历史 |
| GET | `/quota/api/schedule-runs?before=<id>` | 分页读取执行记录 |
| GET | `/quota/api/schedule-runs/<id>?after=<user_id>` | 分页读取逐用户结果 |

编辑、启停、删除要求提交当前规则 `version`；版本冲突返回 `409`，应刷新后重新核对，不要直接重发。
首次分页不传 `before` / `after`，后续使用返回的 `next_before` / `next_after`。

### 停用与回退

平时停用某条规则使用页面开关；暂停所有配额规则时，在页面逐条停用，不需要删除记录。
停止整个应用会同时暂停网页、余额检查与配额定时器：

```bash
docker compose stop statistics
```

停止不清空数据，也不能撤销已经发出的额度请求。重启不重发中断或错过周期的请求。
回退时先停止新应用，再恢复旧镜像及与该版本配套的 Compose，确认不留下新旧调度器并行。
`007`、`008` 均为新增表，可保留规则、执行记录和归档；不要为了回退清空或重建监控库。
